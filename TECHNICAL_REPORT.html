RouteMind — Technical Report

AI-assisted, multi-agent delivery-route optimization for a food bank

Author: Poornesh Muppalam  ·  Professor: Prashant Khanduri

Last-mile logistics VRP with time windows Full-stack   End-to-end technical overview — architecture, subsystems, development journey, engineering decisions, API contracts, configuration, and limitations.

1. Executive Summary

RouteMind plans a food bank's daily delivery van run. A dispatcher adds community delivery sites (by address search or map click), sets each site's serving window and on-site drop time, chooses when the van departs, and asks the system to build the shortest run that still reaches every site inside its window. The result is drawn on a live map as a turn-by-turn route with an estimated arrival (ETA) at each stop.

The core philosophy is a strict split: deterministic math stays authoritative and language models do only what they are genuinely good at.

  • Constraint solver (Google OR-Tools) computes the actual visiting order, honoring time windows, drop times, departure time, and optional ordering pins. Road distances/times come from OSRM.
  • A crew of five agents (LangGraph) wraps the solver with real analysis: input validation, pre-solve conflict prediction, solving, auto-repair of infeasible runs, and advice.
  • Natural-language chat lets the dispatcher edit the run or ask questions; an LLM interprets (with a rule-based fallback) and the deterministic edits are applied + re-solved.

The app runs free and offline-capable: with no API key the chat uses a rule-based parser and agents use computed text; with a free LLM key (Google Gemini by default) the same flows gain natural-language quality.

3. Backend Subsystems

3.1 Solver (solver.py) — the honest core

  • Matrices: road_matrices() fetches real driving durations/distances from OSRM (≤100 stops); on any failure, falls back to a haversine straight-line estimate. Reports distance_source: road | estimate.
  • OR-Tools model: one vehicle, depot = node 0; arc cost = travel time + origin drop time.
  • Time dimension & departure: start cumul fixed to depart_min (defaults to "now"); windows are range constraints; ETAs read back per stop.
  • Horizon fix: max cumulative time = departure + 24h (not a midnight ceiling), so late/long runs don't falsely fail.
  • Pins: "first/last" enforced on the Time dimension's cumulative vars.

  • page.tsx — all app state and flows: add/remove/rename sites (service-area & duplicate guards), the ⚙ per-site conditions editor (drop time + serving window), the "Van leaves at" departure control, Optimize-with-agents (SSE → live panel + repair preview), Solver-only, and the chat (copy / retry / clear + brain badge).

6. Key Engineering Decisions & Trade-offs

  • Math vs. language separation — OR-Tools owns correctness; LLMs never compute the route. Fast, reliable, auditable, and runnable with no LLM.
  • "Leave now" realism — real ETAs can make morning windows infeasible in the afternoon (correct). The editable departure + auto-repair make this usable, not a dead end.
  • Agents that earn their place — narration-only nodes replaced with ones whose decisions change outcomes.
  • Provider-agnostic LLM — one OpenAI-compatible adapter for Gemini / Groq / Ollama / OpenAI, by env vars alone (no lock-in, no subscription).
  • Graceful degradation — no OSRM → estimate; no LLM → rules/templates; unfixable run → honest message.

7. Configuration & Running

Backend (backend/.env):

LLM_BASE_URL=https://generativelanguage.googleapis.com/v1beta/openai/
LLM_API_KEY=<gemini key>
LLM_MODEL=gemini-flash-lite-latest
OSRM_URL=https://router.project-osrm.org

Run: cd backend && source .venv/bin/activate && uvicorn app:app --port 8000

Frontend (frontend/.env.local):

NEXT_PUBLIC_BACKEND_URL=http://127.0.0.1:8000
NEXT_PUBLIC_GOOGLE_MAPS_API_KEY=<maps key, browser-only>
NEXT_PUBLIC_N8N_CHAT_URL=            # blank -> built-in /chat

Run: cd frontend && npm run dev → http://localhost:3000. Keys are separated by surface: the Maps key is public (browser, referrer-restricted); the LLM key is server-side only.

8. Known Limitations & Future Work

  • Single vehicle — multi-van fleet routing not yet modeled (OR-Tools supports it).
  • No live traffic — OSRM gives typical, not live, times; ETAs are honest about this.
  • Public OSRM limits — rate-limited; production should self-host; Diagnostician re-solves are bounded to a few experiments.
  • Service area — hard-coded to Northern California (≤130 mi of base).
  • Vestigial pieces — requirements.txt still lists scikit-learn/numpy (removed learning feature); the n8n/ files and flexible chat parser remain though unused — harmless.
  • Chat scope — one action per turn; compound requests handled sequentially.
